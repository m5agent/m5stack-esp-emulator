## Why the old runner is insufficient

`.work/flashlight-live-probe-20261027/probe.py` and the archived selected runner
call `Pin(..., OUT, value=0)` and wait 600 us at the beginning of every phase.
That would erase the very interval this regression needs to retain. The new
runner initializes M5 and the original driver once and retains its Pin/driver
instance in a nonce-scoped entry of the actual mutable `sys.modules` dictionary.
The first actual narrow-r1 failed before route execution because the initial
prototype used `setattr(sys,...)`; stock MicroPython has fixed `sys` globals
(`py/objmodule.c:86-100`, `py/modsys.c:358,388`). This failure and original cleanup
assessment are preserved separately. Pure route phases have no EN
setter, constructor or M5.begin. Package activation can evict managed modules;
it does not replace this nonce or retained driver instance.

## API lane and exact discrimination

Each requested device/mode gets a fresh visible `/api/v1/sessions` guest in
`program_mode=uiflow-live`. Source packages use public `program-revisions` and
`sessions/{id}/program`, original driver bytes, fresh execution START markers,
and the existing same-VM/runtime identity and cleanup helpers. No direct QEMU
launch, matrix runner, control-plane review or QOM setter is used here.

Default five cases per lane are:

1. 256 -> LEDC73 -> 256, no EN write within the route window.
2. 256 -> RMT81 -> 256, same condition.
3. 256 -> GPIO256 plus OUT_INV -> 256, same condition.
4. LEDC73 interval with a real guest EN fall and 800 us low; return GPIO while
   still low; it must remain unknown through an additional 240 ms of low.
5. Same unsupported 800 us low, followed by return GPIO and immediate rise in
   the same guest segment; no host/API/serial/wait occurs between return and
   rise. The old unsupported low must not grant a new program qualification.

Every atomic case first creates a fresh supported high->low reset interval
of 600 us, executes the unmodified driver single pulse, provides a 20 ms
`sleep_ms` scheduling window for its model latch, and switches away/back in one
guest segment. The initial 600 us busy-wait version is preserved as actual
narrow-r2 FAIL: no decode increment was observed before the route window.
`mphalport.c:195-223` distinguishes task-yielding `sleep_ms` from busy-waiting
`sleep_us`; the corrected narrow-r3 actually observed the mandatory increment.
No event-loop trace was captured to prove the exact scheduling cause.
`ticks_us` verifies
arm-to-return is below 100 ms, ahead of the model's old 220 ms Flash deadline.
This is guest-clock evidence; controller C tests separately inspect virtual
timer ordering. The test requires an actual decode increment before route
invalidation and exact rising/edge increments from only explicit Pin writes.

After returning to GPIO, the test requires `output-known=false`,
`active=false`, `waveform-qualified=false`, internal `program-state=unqualified`,
and cleared settle/timeout deadlines. A 240 ms later observation must preserve
unknown and all edge/decode/reset/timeout counters. No getter call occurs
inside the atomic away/back window. Internal phase/timer observations prevent
a current-route getter mask from being mistaken for lifecycle invalidation.
The public interface has no reset-at-ns: pending reset cancellation is also
checked by stable known/reset counters after the negative low interval.

Recovery requires a newly observed **supported** EN high->low edge and 600 us
low, independently observed known-off/ready-low and reset increment; only then
does the original driver run again. Flash recovery is sampled after 240 ms to
avoid racing nominal expiry across independent QOM fields; it proves the
original single-pulse decode/known expiry, not a guaranteed live Flash-on
screenshot. Torch recovery remains active and is the strong no-deadline
mounted-Web demonstration.

The Pin/PWM companion source generators are prepared separately. Actual
`PWM(...).deinit()` and `Pin(...OUT,value=0)` record their real route readbacks;
they cannot be substituted for the route-pure acceptance sequence or claimed
to supply PWM waveforms. They are not in the default lifecycle execution.

## CoreS3 mounted Web sequence and six evidence categories

Use a separate CoreS3 Torch `--web-only --hold-file <fresh.json>` execution.
The copied observer has been adapted as a new source, not presented as the old
gen42 observer. Initial original-driver Torch active then, for each of LEDC73,
RMT81 and OUT_INV: route-away / GPIO-return-still-unknown / new-supported-reset
known-off / original-driver active. This is 13 separately captured stages.

Each stable stage independently collects all six categories:

1. Session/program/worker/runtime identity: same PID, firmware SHA, worker
   generation, nonce, execution and immutable revision references.
2. Fresh complete UART record after that execution's START, including actual
   MMIO route readback and EN reading.
3. Nonempty actual `/units` response plus independent raw QOM getters,
   including internal phase/deadlines and counters, never response stubs.
4. Valid nonempty current PNG with independently decoded EN center pixel and
   hash/execution/revision headers. The white pad marker stays white during
   unsupported high-route unknown and does not pretend to show lamp output.
5. Actual mounted default UnitPanel / vendor `FixedWhiteLed` instance, runtime
   known flag, physical assembly attachment, fixed white emissive material,
   brightness 0 for unknown, no glow, no active S1 input and no synthetic
   binding. The browser only GETs; commands go to the owner runner.
6. Actual mounted display center pixels and metadata plus framed host-and-Unit
   WebGL, Unit panel, viewport and stage PNGs. Physical events remain zero,
   real default 3D admission is not overridden, and only documented read-only
   state instrumentation is appended to a hash-verified sessions.js response.

HTTP 304 is body-absent by protocol and is never read as an entity. Empty
optional HTTP200 frame captures are separately marked partial and cannot
stand in for mandatory valid frame or mounted-display evidence. Render,
controller, serial and individual getter samples are stable-stage samples,
not one atomic snapshot or proof of an exact browser texture transfer.
