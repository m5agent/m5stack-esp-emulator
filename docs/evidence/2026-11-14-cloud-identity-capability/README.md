# 云端身份能力协商与创建收据复验

日期：2026-11-14。真实固件路径为 **virtual-device validation**；HTTP 兼容性与浏览器协议对照单列。

## 改动与执行身份

旧服务支持云端启动，不等于支持选择设备身份。新客户端现在读取设备目录中
独立的 `device_identity` 能力；只有服务明确支持当前设备和运行时，才显示
身份输入、发送指定 MAC 或默认持久 key。旧服务不会收到可能被静默忽略的
身份参数。收到创建回执后，客户端先保留会话所有权，再校验实际身份；不匹配
时取证并停止，清理未完成时继续保留所有权。未知创建结果仍复用原请求与幂等 key。

实际执行源码为 `3a4408e4a1f26c0c8ad3ff07dae1ac8149a50384`，候选站点为
`c9a3b79f45fdfeac7a4a8eb1eda1b521bea7a35a9da5538b1e35f52199cb0ca8`。
原版 CoreS3 固件 `5847a2bc…`、规范化镜像 `480ca4a2…` 和 Xtensa
`5ce7d9f5…` 未更换；完整 SHA 和执行文件字节映射见
[guest 摘要](guest-summary.json)。本次结果不自动授予其他原版固件、常驻部署或 Pages 发布。

## 保留的失败与观察器控制

第一次授权身份验收在 COI 首次重载后等待认证输入失败，尚未创建 guest。
第二次完成固件观察，但脚本将填写认证信息前的 401 计入运行期，原报告仍为
FAIL。修正后按准备、运行、停止阶段记录所有事件，跨阶段迟到的运行请求
错误仍会失败；只有实际 owned stop 后的对应帧 409 单独计数。第三次独立
195 秒结果如上，没有改写前两次报告。

默认身份首轮在随附 Chromium 下记录了 1,172 个 `ERR_ABORTED`，同时收到
1,172 个 304，运行画面和身份检查通过，整体 FAIL 保留。独立 HTTP 对照分别
切换 CDP、响应头读取和 Service Worker，共两浏览器各八组：两者各 96 次
JavaScript fetch 均成功；Chromium `156.0.8078.4` 同时产生 96 个请求中止事件，
桌面 Chrome `157.0.8103.52` 为零。无 Worker 时也存在该差异，不能据此归因于
产品 Worker。详见[观察器控制与原失败](observer-controls-summary.json)。

新一轮 45 秒显式固定桌面 Chrome，执行前后版本及可执行文件 SHA 相同，
严格网络检查保持不变。195 秒轮次记录了桌面 Chrome 的选择，但未捕获其
历史版本和可执行文件 SHA；该复现限制保留，没有用当前安装反推。

## 复现与未覆盖项

使用独立 Device Service、同一原版参考 SHA 和 `qemu-wifi`。先读取设备目录
的 `uiflow_startup` 与 `device_identity`，分别从实际网页执行留空身份和已授权
身份路径；记录真实 POST/回执、同会话 NIC/eFuse、网络协议、UI 和 ZIP。
授权身份窗口从首次握手后持续至少 195 秒；取证后停止并保留历史。
旧服务控制使用真实旧目录及新客户端，确认拒绝发生在 POST 前，见
[HTTP 摘要](legacy-http-summary.json)。

这些改动不替云端生成绑定关系，也不伪造标准 Pong。云端心跳处理仍未修复；
远程代码执行、物理硬件及 browser-WASM 云端网络均未通过本次验证。
先前[身份、心跳与 COI 故障记录](../2026-11-14-uiflow-cloud-identity/README.md)
继续保留。没有提交 Burner。
