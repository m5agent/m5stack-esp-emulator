# UIFlow2 原版启动与云端配对

## 目标

本地 Device Service 的官方 UIFlow2 入口应保留固件自己的开机菜单、联网和云端
配对流程。成功必须来自同一 guest 的实际云端响应与屏幕；服务连接、虚拟 AP
关联、REPL 就绪或 `M5Things.status()==2` 均不能单独证明取得配对码。

## 已确认的分流

现有本地/浏览器编程环境会替换 `boot.py` 和 `main.py`，主动进入 REPL。
这条路径用于网页运行代码，不能代表官方开机流程。浏览器 WASM 构建未提供公网
网络后端，也不能借用原生服务的联网结果。

独立原生服务已使用未改应用、启动脚本的 CoreS3 原版 UIFlow2，加合法 NVS
网络配置和 `qemu-wifi`，观察到官方界面的非空 Access Code。最终跨设备、页面
及常驻服务验收另记，不从这一例推定所有型号通过。

## 方案

选择增加显式原版启动模式，而非修改既有编程模式或建设浏览器网络代理。
本地页面提供“官方 UIFlow2 · 云端配对”和“本地 MicroPython 编程”两个入口。
原生服务广告支持且用户未显式选择浏览器执行时，官方入口使用原生运行；显式
浏览器模式仍保持原执行选择，并说明云端配对需要原生服务。

Session 请求携带 `uiflow_startup={mode:"cloud",reference_sha256:"…"}`。
能力广告绑定当前参考镜像 SHA。服务在原请求幂等绑定之后验证镜像、设备及字段
冲突，用现有 NVS overlay 在会话 Flash 副本中配置官方字段、`boot_option=1`
及虚拟 AP。应用、官方 `boot.py/main.py` 和不可变参考镜像字节保持原样。

该模式明确使用 `qemu-wifi`，默认关闭无关 HTTP fixture 并保留网络取证。
合法调用者网络策略仍按既有规则验证，不通过启动模式绕过策略。通用上传 BIN、
Preview/Run、UART REPL 和现有显式 NVS 请求保持其各自契约。

## 验收

- 正负契约：参考 SHA、冲突字段、NVS 类型与官方生成器字节等价、幂等重放、
  取消后恢复及编程入口不变。
- 原版路径：多个型号的 DHCP、DNS、SNTP、真实 MQTT 配对回包与官方屏幕，
  绑定固件、NVS、运行时及同一 Session；先取 evidence 再停止并保留历史。
- 本地页面：从用户可见入口实际启动、显示原厂配对页；编程入口仍可运行代码。
- 发布：完整平台与前端契约通过后合入 main，准备可回滚的服务/运行时及导出
  页面，再更新现有常驻实例并从更新后的实例复测。不得提交 Burner。

原始串口和 pcap 可能包含 MQTT 凭据、设备身份与配对码，只留在忽略目录。
公开证据只保留脱敏状态、哈希、计数与协议阶段。
